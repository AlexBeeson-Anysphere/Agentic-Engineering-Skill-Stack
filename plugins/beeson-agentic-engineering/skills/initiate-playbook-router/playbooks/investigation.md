### Investigation

**You own the answer. Plan, route, write.**

Investigation requests are read-only. They produce a cited explanation or a recommendation, not a code change.

1. Route through the Understand capability over the affected subsystem. For motivation questions (why was this built this way), also route through the History capability.
2. Throughput checkpoint stays one line: `throughput checkpoint: n/a, read-only investigation`.
3. If a Feature Map exists, open the one feature file for the area under question and cite it. Answer from the map and the code, not from exploration the map already did.
4. Produce the investigation output: Overview / Key Concepts / How It Works / Where Things Live / Gotchas. For a decision between alternatives, produce a recommendation with a tradeoffs table instead.
5. Cite every load-bearing claim: file, symbol, artifact, or run output. Label anything you did not verify as inferred or guess.

No PR, no babysit, no design exploration unless the investigation precedes a code change. If it does, hand back to the user and re-route to Bug fix or Feature.

**Reply:** the investigation output. For "are we sure?" answers, include your real judgment with reasons. Push back if the premise is wrong.
